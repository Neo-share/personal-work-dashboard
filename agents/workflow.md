# Agent 工作流执行规范

> Agent 工作流定义。入口摘要见 `AGENTS.md`、`CLAUDE.md`。

## A. 路由

- 会修改代码、配置、文档或 CI：执行 S0 至 S5，S3 后必须进入 S4。
- 纯问答：不必 gate，但仍需确认上下文来自当前仓库。
- 用户明确要求计划：停在 S2，等待确认后再进入 S3。

## B. 状态机

```text
S0 上下文确认 → S1 需求结构化 → S2 任务计划 → S3 实施 → S4 验证门禁 → S5 交付报告
```

- S1/S2 默认须人类确认。小而明确的单文件改动可合并说明，但仍要明确将修改哪些路径。
- G.2 改动范围确认不可豁免：S3 写入前必须确认具体文件路径或路径集合。
- 禁止跨状态写库：未进入 S3 不写代码，未完成 S4 不宣称完成。

### B.1 外部交互前环境自检

涉及 DB、Docker、网络、MCP、浏览器自动化、E2E 前，先确认依赖、登录态、服务地址和风险。发现需要人工操作时停止并说明阻塞。

### B.1a E2E 前自检

裸 Playwright / 浏览器 E2E 前先做 preflight：确认依赖安装、浏览器可用、本地服务地址可访问。缺浏览器或服务未起时，先报告或按用户要求启动。

## C. 全局禁止

- 禁止 `pnpm agent:gate` 未通过就宣称完成。
- 禁止越过 G.2 直接写入未确认路径。
- 禁止 CI 自动 commit、自动修改源码或写回分支。
- 禁止回滚用户已有改动，除非用户明确要求。

## D. 命令速查

见 **[commands-checklist.md](./commands-checklist.md)** §Agent 命令。

## F. 分阶段执行卡

### S0 上下文确认

- 输入：用户原始请求、当前仓库、git 状态、相关规则。
- 执行：确认任务类型、影响域、是否需要技能或 MCP。
- 输出：一句话说明理解和第一步。
- 失败回退：需求不清时询问，不做猜测性写入。

### S1 需求结构化

- 输入：用户目标、已有代码和文档。
- 执行：整理目标、非目标、验收标准、风险点。
- 输出：简短 Spec；复杂任务等待用户确认。
- 失败回退：标出缺失信息并暂停。

### S2 任务计划

- 输入：S1 Spec、项目 baseline。
- 执行：列出预计改动文件、scope、验证命令、回滚思路。
- 输出：计划和 G.2 改动范围确认。
- 失败回退：范围争议未解决前不进入 S3。

### S3 实施

- 输入：已确认的 S2 文件清单。
- 执行：最小改动，遵守包依赖方向和本项目编码约束。
- 输出：实际改动文件。
- 失败回退：只撤回本轮 Agent 自己的改动。

### S4 验证门禁

- 输入：实际改动。
- 执行：I.0 scope 两步校验，再跑 `pnpm agent:gate`。
- 输出：命令结果和剩余风险。
- 失败回退：先跑 `pnpm agent:s4:mechanical-loop`，仍失败则认知修验，上限 15 轮。

### S5 交付报告

- 输入：git diff 实单、验证结果。
- 执行：对比 S2 计划与实际，说明未完成项。
- 输出：简洁交付说明；不自动 commit。

### F.6 改动文件信息链

S1 触点 → S2 文件清单 → 人类确认 → S3 实施 → S5 git diff 对比。任何新增路径都要在进入写入前补充说明。

## G. 人类确认与 Follow-up

- G.1 同会话 follow-up：可用极简 S1 + G.2 + I.0 + S4。
- G.2 改动范围确认强制不可豁免。

## I. CI 与开发环境

- I.0 改代码后 scope 两步校验：`pnpm agent:scope:auto` → `pnpm agent:scope:<scope>`。
- I.1 CI 只验证，不写库、不格式化提交、不生成 commit。
- I.3 S4 认知修验循环默认上限 15 轮；超过后交付失败原因和下一步。
