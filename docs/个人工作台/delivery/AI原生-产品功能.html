无 AI 时如何实现 · 引入 AI 后如何重构 · 个人 AI 助手工作台 · 核对日期 2026-07-09

交付说明 架构设计 测试用例 测试报告 AI原生·技术 AI原生·产品

1. 一段话说明

无 AI 时，个人工作台是一套本地 CRUD 应用：用户通过表单和筛选管理待办与日程，定时任务到期后物化为待办；自然语言入口退化为关键词规则（「会议纪要→待办」「明天开会→日程」），所谓「AI 结果」只是按类型填充的固定 HTML 模板，与用户当日日程、历史纪要毫无关联。引入 AI 后，产品骨架不变（调度层→工作单元→待办层三层不变），但待办层被重构为「能力判定 → 内部知识检索 → LLM 生成/修订 → 版本回溯」的闭环：创建待办时从 SQLite 召回相关日程块与历史已确认结果作为上下文，LLM 产出有依据的结构化 HTML；多轮修改时追加对话线程与 RAG 片段；意图分流、定时调度、护栏拦截仍由确定性规则引擎承担，LLM 仅在高价值生成环节介入，且未配置 Key 或调用失败时自动降级回规则模板——因此 AI 不是外挂插件，而是嵌入待办工作流的可选增强层，主链路在无 AI 环境下仍可完整运行。

工程侧如何用 AI 写代码落地，见 AI原生·技术实现篇。

3. 档 P0：无 AI 基线（产品完整可用）

P0 · 确定性产品

即使完全不配置 LLM_API_KEY，以下产品能力全部可用，满足考题 Demo 与日常管理需求。

3.1 待办管理（L1-02）

能力无 AI 实现
四态筛选进行中 / 全部 / 已完成 / 已逾期；SQL 条件查询
手动添加弹窗表单 → todos.create
完成归档勾选移入历史区；支持恢复与删除
逾期标记服务端比较 due_at 与当前时间
AI 入口条展示「已生成结果 / 正在生成」；内容为规则模板

3.2 日程管理（L1-03）

能力无 AI 实现
0–24h 时间轴按日查询 schedule_events
四渠道开关飞书/钉钉/Outlook/本地 seed mock
15 分钟去重同标题同时段合并展示
NL 写入日程规则识别「会议/面试/出差」→ 只写日程，不建待办

3.3 定时任务（L1-04）

能力无 AI 实现
重复规则每天 / 每周 / 每月 CRUD
物化待办调度器 60s tick → 创建 source=recurring 待办
日滚动同一规则每日最多物化 5 条
与 AI 关系调度层不调模型；物化后可触发 P0 模板或 P1 LLM

3.4 个人助手（L1-05）— 规则引擎

能力无 AI 实现
NL 三分流IntentRouter 关键词 → 待办 / 日程 / 定时
能力判定detectCapability 正则：「纪要→minutes」「复盘→review」等
需人工拦截含「电话/回访/线下/见面/签字」→ 不自动生成
四层护栏注入检测、敏感动作、路径脱敏 — 确定性代码
修改模式进入 revise 线程；无 LLM 时修订仍走模板替换逻辑

3.5 AI 结果（L1-06）— 模板态

结果类型无 AI 模板内容
minutes固定进度/要点/结论占位 HTML
review固定统计卡片 + 结论文案
audit固定合规清单 checkbox 列表
plan / report / analysis / pick各类型预设 HTML 骨架

模板由 generateAiHtml() 产出；Soul 语气（正式/友好）仅影响模板前缀，不涉及 LLM。

4. 档 P1：引入 AI 后的待办层重构

P1 · LLM 生成/修订

配置 LLM_API_KEY 后，仅待办层的「AI 初步结果」与「多轮修改」从模板升级为 LLM 驱动；其余 P0 能力不变。

4.1 触发链路

待办创建（手动 / NL / 定时物化）
  → detectCapability(title) → canAuto ?
       ├─ false → aiStatus=manual，无生成
       └─ true  → aiStatus=pending → scheduleAiResultGeneration（异步 1.5s）
            → retrieveForTodo（P2 RAG，可无）
            → generateAiResultWithLlm
            → todo_ai_results v1 + aiStatus=ready
            → 前端轮询 / refresh 展示 AiResultPanel

4.2 与 P0 的差异

环节P0 模板P1 LLM
内容来源硬编码占位数据待办标题 + RAG 片段 + Soul 偏好
纪要类通用「讨论进行中 60%」引用当日相关日程块与历史纪要
多轮修改简单字符串替换reviseAiResultWithLlm 全量修订 + 版本递增
确认完成标记 confirmed → 待办 completed同左，逻辑不变
失败处理—自动降级 generateAiHtml，provider 记为 rule-template

4.3 七类 AI 结果（P1 生成目标）

类型典型待办标题P1 生成侧重
minutes做会议纪要进度 + 要点 + 结论；引用当日会议日程
review周复盘统计卡片 + 周期内已完成待办摘要
audit合规审核清单式 checkbox 结构
planUI 改版方案背景 / 步骤 / 风险
report月度报告摘要 + 指标列表
analysis数据分析表格化指标对比
pick基金选品选品分析结构化输出

5. 档 P2：内部 RAG 知识闭环

P2 · 有依据的 AI

RAG 不改变产品交互，但让 P1 生成从「看起来像 AI」变为「有内部依据的 AI」。数据均在 SQLite 内闭环，不依赖外部 OAuth。

5.1 检索源（R0 规则检索，已实现 E1–E3）

数据表检索用途
schedule_events纪要类：截止日前后日程块（「会议发生了什么」）
todo_ai_results同主题历史已确认版本；同类型 few-shot 参考
todos同周期已完成待办；主题聚类
assistant_messages多轮修改：当前线程最近 N 条对话
recurring_tasks定时来源说明、物化历史

5.2 两条高价值链路

链路触发RAG → 产出
初步生成待办创建且 canAuto召回日程 + 历史纪要 → LLM HTML v1
多轮修订助手修改模式 + revise 指令v1 全文 + 对话 + 日程 → LLM HTML v2…

5.3 明确不做 RAG 的产品能力

能力原因
NL 意图分流分类问题，继续规则引擎
定时任务调度确定性逻辑
Soul 偏好向量库体量小，prompt 注入即可

6. 档 P3：可选扩展

P3 · 增强项（非考题必交）

未配置时不影响 P0–P2 主链路。

8. 端到端用户场景对比

8.1 场景 A：「帮我做会议纪要」

步骤P0 无 AIP1+P2 有 AI
1. 用户输入个人助手 NL同左
2. 分流规则 → 创建待办「做会议纪要」同左
3. 能力判定命中 minutes → canAuto=true同左
4. 生成1.5s 后展示固定模板 HTMLRAG 召回当日「产品需求评审」日程 + 上次纪要 v2 → LLM 生成
5. 修改「补充结论」→ 模板字符串替换召回 v1 + 对话 → LLM 写 v2
6. 确认待办自动完成同左

8.2 场景 B：「明天下午三点产品评审」

步骤P0 / P1 均相同
分流规则识别为日程，不创建待办
写入schedule.create_local → 时间轴展示
AI 参与无 — 会议类只写日历

8.3 场景 C：定时「每周一写周报」

步骤P0P1
调度周一 tick → 物化待办同左
AI模板 report HTMLLLM + 检索本周已完成待办片段
原则定时任务 Tab 本身不调模型，AI 仅在物化后的待办层触发

9. 设计原则（AI 原生 vs AI 附加）

  1. AI 原生 ≠ 处处调模型：分流、调度、护栏、CRUD 保持 P0 确定性；LLM 只负责待办层高价值生成。
  2. 降级即契约：无 Key、超时、失败均回退 P0 模板，Demo 与生产同一套代码路径。
  3. RAG 先于 Prompt：P2 先检索 SQLite 内知识，再调 LLM，避免「裸生成」。
  4. 三层能力分层不可打破：调度 → 工作单元 → AI，防止职责与成本失控。
  5. 用户无感切换：同一 UI（AI 入口条、面板、修改模式）；P0/P1 差异仅在内容质量与 provider 标识。
