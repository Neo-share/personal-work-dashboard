2. 协作分工模型

人 · 定界与验收
  • 编写/审定产品需求原文（个人工作台.md）
  • 冻结 T0 架构：三层能力分层、Monorepo 包边界、五层助手、数据流
  • S1/S2 确认需求与改动范围（G.2 路径集合）
  • 审阅 AI 生成的 L4 / TL4 文档与测试用例
  • 验收黄金话术、护栏拦截、降级路径等关键行为
AI Agent · 吞吐与一致性
  • 需求 → L4 产品功能点分解（119 条，可判定 ✅/❌）
  • L4 → TL4 技术映射（组件 / service / router / DB 表）
  • 按 TL4 批量实现 client / server / shared 代码
  • 生成 Vitest 单测、集成测、黄金话术回归（97 条）
  • 门禁失败时机械修复或认知修验（上限 15 轮）
人定 T0 边界
    ↓
AI 生成文档链（L4 → TL4 → 测试清单）
    ↓
AI 按 TL4 写代码 + 测例
    ↓
Agent 控制层：scope 校验 → agent:gate:dev → 完成判定
    ↓
人验收关键路径 + 交付文档

9. 经验总结：可复制的协作公式

成功交付 ≈ 人定边界 × AI 吞吐 × 客观门禁 × 编号追溯

1. 人先写「不能错」：架构、安全、验收口径（T0）
2. AI 再写「可以批量」：CRUD、组件、测例、文档映射（T1–T3）
3. 门禁兜底「不能宣称完成」：scope + test + build（T4）
4. 人最后验「不能自动化」：UX 细节、黄金话术、降级体感（S5）

9.1 推荐协作节奏（单需求）

  1. S0：确认影响域（client / server / shared / docs）
  2. S1/S2：列 L4 编号 + G.2 文件清单，等人确认
  3. S3：加载对应 Skill，最小改动实现
  4. S4：pnpm agent:scope:auto → pnpm agent:gate:dev
  5. S5：更新功能点状态 + 交付说明（若对外）

9.2 不推荐的做法

  • 无 T0 边界直接让 AI 「从零搭全栈」——后期重构成本极高
  • 跳过 G.2 范围确认——易产生跨包改动与 merge 冲突
  • 只靠人工点测、不跑门禁——回归不可复现
  • 把分流/护栏/调度交给 LLM——安全与成本不可控
